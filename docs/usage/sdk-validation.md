# Local minimum/latest SDK compatibility

Run `scripts/sdk_compat.py` to check fresh Dust generation on explicit minimum
and latest-stable Dart/Flutter installations. This is a local test gate, not a
release or an assurance that every new Dart language feature is supported.

The core runtime packages declare Dart >=3.6.0. Test standalone Dart 3.6.0
separately from the minimum Flutter target, 3.29.0 / Dart 3.7.0. Flutter 3.27
pins `meta 1.15.0`, incompatible with Dust's existing `meta ^1.16.0` constraint;
its consumer Pub resolution failed and is not counted as a passing target
([Flutter 3.27 manifest](https://github.com/flutter/flutter/blob/3.27.4/packages/flutter/pubspec.yaml)).
Flutter 3.29 supplies `meta 1.16.0`
([manifest](https://github.com/flutter/flutter/blob/3.29.0/packages/flutter/pubspec.yaml)).
No production constraint or SDK pin is
overridden to hide that boundary. SQLite has a separate stable Dart 3.10.0
floor: use its [independent consumer/native gate](db-sdk-validation.md) too.
Do not lower SQLite's constraints to make it run on the core floor.

## Run

Requirements: Python 3.10+ with working HTTPS trust, Cargo, Puro and already
installed SDKs. The script never installs an SDK or changes the selected one.
Supply exact binary paths and Puro environment names:

```sh
python3 scripts/sdk_compat.py \
  --minimum-dart /path/to/flutter-3.27.0/bin/cache/dart-sdk/bin/dart \
  --minimum-flutter-env dust_flutter_3290 \
  --latest-dart /path/to/latest-dart/bin/dart \
  --latest-flutter-env dust_latest
```

`CARGO_TARGET_DIR` can reuse an existing local build cache. The runner builds
the Rust CLI from this checkout; it does not use an installed release binary.
On Windows, supply `dart.exe` paths. This command is not Windows execution
evidence until it actually passes there.

The runner refreshes Puro's stable Flutter listing and official Dart stable
metadata before testing. An outdated supplied SDK, failed refresh, prerelease,
wrong minimum or mismatched Flutter/Dart pair cannot produce a passing result.
If stable Dart and Flutter bundle different Dart patches, supply the latest
standalone Dart separately; each compiler is recorded under its own target.
Network access is needed for metadata and initial Pub resolution, not remote
CI or application HTTP services. HTTPS verification is never disabled. Configure
Python's trusted CA bundle if necessary; macOS installations can use
`SSL_CERT_FILE=/etc/ssl/cert.pem` when that is their trusted system bundle.

## What is checked

For both SDK ends, the runner stages independent source copies outside the
workspace and preserves the original manifests. Pub overrides reset workspace
resolution, select source Dust packages and choose SDK-compatible development
lint tooling. Production constraints, source files, root locks and SDK defaults
are unchanged. Pub resolves allowed dependencies independently; this is not
the repository lock running on every SDK.

1. Copy the real Dart product showcase and Flutter benchmark consumers.
2. Remove their copied `.g.dart` files and Dust-banner-marked HTTP auxiliary
   tests, including legacy plain `.dart` test filenames. Stale
   committed output cannot rescue missing generation. Originals are untouched.
3. Resolve with the exact SDK; record dependency graphs. Generate the benchmark's
   documented 64-model source corpus using that SDK, not copied ignored files.
4. Freshly run `dust build --clean` and `dust check`; require every previously
   present generated file to be recreated and record all generated hashes.
   Require identical generated bytes at both SDK ends for each consumer.
5. Analyze with fatal infos and run the complete consumer suites. These cover
   derive, JSON, copyWith, validation, HTTP, row mapping and Flutter route/state
   behavior exercised by those examples; they are not every package or feature.
   Also evaluate the [shared static-literal corpus](../design/static-dart-literals.md)
   on both standalone Dart endpoints with LF, CRLF and CR files, and verify real
   Unicode/hex-escaped imports. Probe tests use owned staging and are removed
   after success or failure; baseline generated hashes stay separate.
6. On the latest Dart SDK, stage `fixtures/primary_sdk_consumer` independently,
   remove any copied generated output, and run fresh Dust build/check plus
   online DB build/check and an offline DB check. Require all seven
   model/client/database `.g.dart` files and complete SQLite metadata for all
   five terminals in both direct-query and DAO libraries. The probe removes
   host `DUST_DATABASE_URL` from its subprocess environment, so validation uses
   an owned in-memory schema. Check handwritten formatting, analyze with fatal
   infos, and execute derive, JSON, validation, enum, HTTP, private row mapping,
   checked direct/DAO queries, sync/worker SQLite and nullable/nested copy tests.
   Repeat with `fixtures/primary_flutter_consumer` on latest Flutter, requiring
   the generated state and route files and running route, state and widget
   tests. Both fixtures require Dart 3.13; neither raises the runtime SDK floor.
   Generic copy cases include bounds, aliases/FutureOr, records/callbacks,
   nested/private boundaries and nullable instantiations. At both traditional
   Dart endpoints and in the primary Dart consumer, analyze the new generic
   source/parts with strict casts/inference/raw types and without the broad
   generated lint ignore. Run five expected kernel-compilation failures per
   consumer; unrelated errors cannot satisfy them.
7. Independently analyze a valid named concise `new` sample. Dust build/check
   must still reject it with the
   feature-specific `Dust does not support ... yet` error, exit 1 and no generated
   output. SDK acceptance is not Dust support; a generic parse error or unrelated
   failure cannot satisfy this negative probe.
8. In owned staging, generate the isolated `fixtures/generic_names` collision
   snapshots using traditional headers at both Dart endpoints and primary
   headers on the latest compiler. Analyze source/parts with strict language
   options and record only the intentional `avoid_types_as_parameter_names`
   and `camel_case_types` infos from unusual binders; warnings, errors and all
   other lint codes fail. No suppression is added. Execute four runtime tests,
   require complete reported line coverage of that generated part without
   coverage-ignore directives, and retain its hash/diagnostics/LCOV separately
   from the ordinary consumer hashes. Remove only the probe's new staged files
   and restore analyzer/generated bytes even when a probe fails. The original
   checkout stays untouched. These checks do not establish every generic
   capability; see [the generic design](../design/generic-models.md).
9. Generate `fixtures/generic_validation` in owned staging on all four SDK ends,
   plus latest Dart/Flutter primary-header consumers. Strictly analyze source,
   parts and tests without broad generated lint suppression. Execute required,
   custom, nested, nullability, bounded/compound-type and exception contracts.
   Explicit typed derive constructors exercise unprefixed and qualified/trivia
   spellings with nested generic arguments, without changing output bytes;
   Flutter also executes concrete and receiver-dependent form helpers. Require
   100% reported executable-line coverage of these three generated libraries,
   without honoring their coverage-ignore markers, and exact validation hashes
   across SDK ends and traditional/primary spellings. Two kernel-negative checks
   per consumer reject wrong helper receiver/candidate types. Baseline generated
   hashes must stay unchanged; every owned source/generated/test file is removed
   and temporarily changed analyzer/source bytes restored even after failure.
10. Generate the three `fixtures/generic_serde` libraries on those same six
    targets: four ordinary SDK rows and latest Dart/Flutter primary consumers.
    Require exact complete snapshots and identical traditional/primary bytes.
    Strict analysis without broad generated lint suppression records only the
    intentional name-style infos from collision binders. Eight runtime contracts
    cover typed factories/directional codecs, dependent bounds, named
    constructors, defaults/aliases, strict keys, nullable values, collections,
    custom codecs and captured core/local names. Require full reported generated
    executable-line coverage (203 lines across the three libraries), ignoring no
    coverage markers. Four expected kernel failures per target reject wrong
    result/receiver/bound uses and erased deserializer results. Baseline hashes
    must remain unchanged, and owned staging is cleaned even after failure.
    Applied inheritance and generic sealed redirects are separate pending gates,
    not established by these ordinary-model tests.

Lint-tool selection is 7.0.0 on the core floor, 10.1.0 on Dart 3.10/3.11 and
10.3.0 on 3.12+. The staged floor options omit only the already-disabled
`remove_deprecations_in_breaking_versions: false` and
`unnecessary_ignore: false` entries: Dart 3.6 does not recognize those newer
rule names. Enabled checks are never removed. Latest options are byte-identical
to the original; Flutter's automatic options migration is not used to relax them.

The benchmark explicitly declares `test: ^1.25.15` as a development dependency
because generated HTTP tests import it. Workspace resolution previously masked
that missing direct dependency. The range permits Flutter 3.29.0's pinned
`test_api 0.7.4`; `test >=1.26.0` would conflict with that SDK pin. Newer SDKs
can resolve newer compatible test releases. No production dependency is added
or upgraded, and SDK pins are not overridden.

Each run retains an owned temporary evidence directory with numbered logs,
refreshed release metadata, independently resolved locks and `proof.json`.
The proof is written only after all four SDK/consumer rows, the positive primary
consumers and the concise negative sample pass. It records source commit/dirty
state, CLI hash, exact SDK versions
and generated output hashes. A failed run retains diagnostics, not a pass proof.
Keep the source commit clean when collecting final review evidence.

## Ordinary local gates

`./scripts/test.sh` runs the offline staging, SDK-validation, failure-propagation
and negative-probe regression tests. Those tests do not require SDK downloads,
Puro or network. The full SDK matrix is an explicit local command, so a machine
without an old SDK does not silently claim minimum compatibility.

No Actions workflow is added or dispatched. Keep only the existing manual Rust
release workflow enabled. No package/CLI version bump or publication is implied.
Physical-device, Windows and storage-readiness gates in SQLite epic #19 remain
separate; simulator or consumer results do not complete them.
